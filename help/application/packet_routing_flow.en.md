# Packet routing rules

This is the full help file for both `Packet Routing` and `Packet Flow`. It covers the screen purpose, common use cases, rule order, filter blocks, target blocks, and ready-made rule layouts.

## What this screen does

A routing rule tells APRSBox what to do with a packet after it is received or generated locally.

Each rule has:

- one source,
- zero or more filter or rule blocks in the middle,
- one final target.

Packets always move from top to bottom. If any block rejects a packet, later steps are not executed.

## How to read and build a rule

The simplest way to think about a rule is:

1. Where the packet enters.
2. What conditions it must pass.
3. Where it should end.

Recommended build order:

1. Choose the source.
2. Choose the target.
3. Add only the filters you really need.
4. Save the rule and inspect the execution log.

## Common use cases

### `Receiver RF -> TX APRS-IS`

This is the classic iGate path.

Minimal layout:

```text
Receiver RF -> Strict Filter -> TX APRS-IS
```

Use it when:

- locally heard RF traffic should be forwarded to APRS-IS,
- different RF ports should have different Internet uplink rules,
- RF ingress should stay separate from locally generated traffic.

Important notes:

- `Strict Filter` is mandatory,
- not every RF-received frame should enter APRS-IS,
- this is an uplink path, not a digi path.

### `Receiver RF -> TX RF`

This is the classic digipeater path.

Minimal layout:

```text
Receiver RF -> Path rule and DIGI guard -> TX RF
```

More typical layout:

```text
Receiver RF -> Duplicate Filter (viscous-delay) -> Path rule and DIGI guard -> TX RF
```

Use it when:

- you want to repeat APRS traffic on RF,
- you are building a local digi,
- you want cross-band or RF port-to-port forwarding,
- you want selected traffic classes to continue after extra filtering.

Important notes:

- `Path rule and DIGI guard` is required,
- `Duplicate Filter (viscous-delay)` is usually a good first step,
- this is the path where RF channel protection matters most.

### `Local TX -> TX APRS-IS`

This path is for frames generated by APRSBox itself.

Layout:

```text
Local TX -> Strict Filter -> TX APRS-IS
```

Use it when:

- beacons, status, weather, objects, bulletins, or messages should go to APRS-IS,
- application-generated traffic needs an Internet uplink path.

Important notes:

- `Local TX` is not RF-received traffic,
- it is a separate internal stream,
- `Strict Filter` is still mandatory.

### `Receiver RF -> Black Hole`

This is a test and diagnostic path.

Layouts:

```text
Receiver RF -> Black Hole
```

or:

```text
Receiver RF -> Direct Only -> Black Hole
```

Use it when:

- you want to test filters without forwarding,
- you want to observe a specific RF port,
- you want to validate a rule before enabling TX RF or TX APRS-IS.

### `Local TX -> Black Hole`

This is a diagnostic path for internally generated traffic.

Use it when:

- you want to see what APRSBox is generating,
- you want to test objects, status, weather, or bulletins without forwarding them.

## Source blocks

### `Receiver RF`

Source for packets received by a selected radio modem.

Use it when:

- the rule should react to traffic from the air,
- several RF receivers need separate routing logic.

In practice:

- every `Receiver RF -> ...` rule begins here,
- the selected modem decides which input can enter the rule.

### `Local TX`

Source for frames generated locally by APRSBox.

It includes:

- beacons,
- status packets,
- weather,
- objects,
- items,
- bulletins,
- messages.

It does not include:

- RF-received traffic,
- already digipeated traffic,
- ordinary TNC input traffic.

In practice:

- this is the internal application transmit stream,
- `Local TX` can lead only to `TX APRS-IS` or `Black Hole`.

## Filter and rule blocks

### `Strict Filter`

This is the system safety block for rules ending in `TX APRS-IS`.

It:

- rejects packets with `TCPIP` or `TCPXX`,
- rejects packets marked `NOGATE` or `RFONLY`,
- validates third-party frames,
- validates the outer and inner paths of third-party traffic,
- keeps unsuitable traffic away from APRS-IS.

Use it:

- always with `TX APRS-IS`,
- never as a replacement for RF digi path control.

Typical use cases:

- `Receiver RF -> Strict Filter -> TX APRS-IS`,
- `Local TX -> Strict Filter -> TX APRS-IS`.

### `Path rule and DIGI guard`

This is the most important block for flows ending in `TX RF`.

It:

- analyzes the digi path,
- decides whether the local station should still repeat the packet,
- blocks locally addressed APRS messages and queries,
- blocks third-party traffic that should not be repeated,
- blocks frames already repeated by the same local station.

Why it is required:

- without it, an RF retransmit rule has no basic digi protection,
- this block provides the core path logic for safe on-air repeating.

Configuration fields:

- `Paths (TRACE / traced)`:
  Aliases or explicit hops that should be consumed while inserting the local digi callsign into the path.
- `Paths (NO TRACE / not traced)`:
  Aliases or explicit hops that should be consumed without inserting the local digi callsign.

In practice:

- `WIDE1-1` is often configured as traced,
- the no-trace list depends on local network policy,
- this block usually sits near the end of the filter chain, right before `TX RF`.

Typical layout:

```text
Receiver RF -> Duplicate Filter (viscous-delay) -> Path rule and DIGI guard -> TX RF
```

### `Duplicate Filter (viscous-delay)`

This block opens a short listening window after a frame enters the flow.

It:

- waits for the configured window,
- checks whether another digi has already repeated the same frame,
- drops the frame if a duplicate repeat is heard,
- passes the frame onward if no duplicate repeat is heard.

Important behavior:

- it can appear only once,
- it should be the first filter in an RF retransmit flow,
- it is most useful in classic digi rules.

Use it when:

- duplicate repeats should be reduced,
- several digis may hear the same source station.

### `Direct Only`

This filter passes only packets heard directly.

That means:

- the path must not contain any already consumed digi hop,
- if the path contains consumed elements marked with `*`, the frame is rejected.

Use it when:

- the rule should react only to directly heard stations,
- already repeated traffic should be ignored,
- you want to inspect direct coverage separately.

### `DIGI Filter`

This filter examines consumed digi hops in the path.

How it works:

- it matches only already consumed hops,
- patterns support `*`,
- `allow` passes only matching packets,
- `deny` rejects matching packets.

Examples:

- `SR5ABC`,
- `SR5*`,
- `*`.

Use it when:

- only traffic from selected digi chains should pass,
- traffic arriving through specific digis should be excluded.

### `Callsign Filter`

This filter matches the source callsign.

How it works:

- it operates on the packet source callsign,
- it supports wildcard `*`,
- `allow` behaves like an allowlist,
- `deny` behaves like a blocklist.

Examples:

- `SQ9MDD`,
- `SQ9MDD*`,
- `SP*`.

Use it when:

- club, test, service, or operator traffic should be separated,
- a known source should be blocked or isolated.

### `Packet Type Filter`

This filter works on APRS packet groups.

Accepted values are:

- `position`,
- `object`,
- `item`,
- `message`,
- `status`,
- `weather`,
- `telemetry`,
- `query`.

Practical meaning:

- `message` also covers ACK/REJ, bulletin, and announcement,
- `weather` means weather-only frames,
- a position with weather data still counts as `position`.

Use it when:

- positions, objects, messages, or weather should be routed differently,
- one rule should be limited to one traffic class.

### `Icon Filter`

This filter matches the APRS symbol in `table+code` form.

Examples:

- `/>`,
- `\\l`.

Use it when:

- selected symbol classes should get their own path,
- symbol meaning matters more than packet type.

### `Distance Filter`

This filter passes a packet only when its decoded position falls inside at least one configured zone.

How it works:

- 1 to 3 zones may be configured,
- each zone has a center and a radius,
- the zones are evaluated with OR logic,
- packets without a decodable position are not automatically rejected by this filter.

Use it when:

- traffic should be limited to a geographic area,
- local-only routing should depend on coverage area or event area.

### `Rate Limit Filter`

This filter limits how often packets from a callsign or callsign pattern may continue.

Rule format:

```text
CALL_OR_PATTERN - LIMIT
```

Examples:

```text
SQ9MDD-7 - 30s
SQ2IDB* - 10s
* - 20s
```

How it works:

- it tracks the time since the last passed frame for each matching pattern,
- the next frame is blocked if it arrives before the limit expires.

Use it when:

- very active stations generate too much traffic,
- an RF path needs soft traffic control without a full block.

## Target blocks

### `TX RF`

This target sends the packet through the selected radio modem.

Use it for:

- local digi paths,
- cross-band forwarding,
- RF port-to-port forwarding.

Typical layout:

```text
Receiver RF -> Duplicate Filter (viscous-delay) -> Path rule and DIGI guard -> TX RF
```

### `TX APRS-IS`

This target sends the packet to APRS-IS.

Use it for:

- iGate uplink,
- locally generated APRSBox traffic that must reach APRS-IS.

Important limitation:

- this target always keeps the mandatory `Strict Filter`.

### `Black Hole`

This is a diagnostic target. The packet ends there and is not forwarded further.

Use it for:

- testing,
- traffic observation,
- validating filters before enabling transmission.

## Editor constraints

- A rule always has one source and one target.
- `Local TX` can lead only to `TX APRS-IS` or `Black Hole`.
- `TX APRS-IS` always keeps the mandatory `Strict Filter`.
- `TX RF` requires an active `Path rule and DIGI guard`.
- `Duplicate Filter (viscous-delay)` may appear only once.
- `Distance Filter` may appear only once.
- `Rate Limit Filter` is intended for flows ending with `TX RF`.

## Ready-made layouts

### Simple RF iGate

```text
Receiver RF -> Strict Filter -> TX APRS-IS
```

### Classic RF digi

```text
Receiver RF -> Duplicate Filter (viscous-delay) -> Path rule and DIGI guard -> TX RF
```

### Digi for directly heard stations only

```text
Receiver RF -> Direct Only -> Duplicate Filter (viscous-delay) -> Path rule and DIGI guard -> TX RF
```

### Locally generated traffic to APRS-IS

```text
Local TX -> Strict Filter -> TX APRS-IS
```

### Diagnostics without forwarding

```text
Receiver RF -> Black Hole
```

## Good practice

- Choose the source and target first, then build the conditions.
- For `TX RF`, think about channel protection before coverage.
- For `TX APRS-IS`, make sure only suitable traffic reaches the Internet side.
- During testing, start with `Black Hole`.
- After saving, use the execution log to see exactly which step passed or rejected the packet.
